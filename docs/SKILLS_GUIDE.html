Claude skills guide

A self-study tutorial for the team. It teaches which skill, agent, hook or plugin to use in Santolina_tutor, and when. Each module has questions, a reference table and a trap. An A to Z index is at the end. You need Claude Code and a clone of this repository. Checked on 2026-11-14.

How to use this guide

This guide is based on the method of the socratic-tutor skill. You answer a question first. You read the explanation after you commit to an answer.

Four terms come first:

  • A "skill" is a set of instructions that Claude loads for one type of task. You start a skill in two ways. Type /name, or write a request that matches its trigger words.
  • An "agent" is a separate Claude worker with its own instructions and tools. A skill or Claude can start it.
  • A "hook" is a script that Claude Code runs on its own before a tool call, for example before a shell command.
  • A "plugin" is a package of skills, agents and commands from a marketplace. Plugin skills have the form plugin:skill, for example /devils-advocate:adversarial-review.

In this guide, "tool" means any skill, agent, hook or plugin command.

  1. Write each answer down before you open it. Count only written answers.
  2. Do the diagnostic. Its questions cover modules 1, 2, 5 and 7. A wrong answer sends you to that module.
  3. For the other modules, do the "Level 4 test" on the skill map. Read every module where you fail the test or the diagnostic.
  4. In each module, answer the "Predict" questions first. The reference table comes after them.
  5. Do each review block on a later day if you can. If you miss a review question, lower that module by one level and read it again.
  6. Each module ends with a "Trap": a wrong claim. Write what is wrong with it before you open it. Level 5 needs this.
  7. Do the final test without scrolling up. The pass rule is at the end of the test.
  8. Keep a note with one line per module and your level (0 to 5). Update it after each review block and after the final test.

Tags in the tables: read-only does not change files. writes changes files. automatic runs without a request.

Diagnostic

Write your answer to each question before you open it. The questions go from easy to hard.

  1. The language model service on the board does not answer. Which skill do you ask for?
    Answer

    unoq-board. It knows the two services math-llm (port 8081) and math-embed (port 8082), and it has a table of symptoms and fixes. Module 2.

  2. You want to add a hint feature to the copilot and know if accuracy goes down. Which skill?
    Answer

    m3kang-copilot. It keeps the predict.py contract and runs eval.py, which adds one row to results/ablations.csv per experiment. Module 2.

  3. Claude runs git add -f data/train.jsonl for you. What happens? What happens if you type the same command in your own terminal?
    Answer

    When Claude runs it, the m3kang-guard hook stops the command before Git runs. The -f flag does not help. When you type it in your own terminal, nothing stops it. Git stages the file. The hook guards only the commands that Claude runs. Module 1.

  4. The README is out of date after a week of code changes. You do not want any edits yet, only a list of problems. Which skill?
    Answer

    docsauditor. It is read-only and lists each drift (a place where the docs no longer match the code) with a status. docsjanitor is the skill that makes the edits. Module 7.

  5. Your ablation table (results/ablations.csv, one row per experiment) shows +4 points for a new prompt. A teammate says the validation set leaked into the prompt examples. Which tool attacks that claim, with which lens (the expert view that the reviewer takes, see module 5)?
    Answer

    /devils-advocate:adversarial-review with the data-scientist lens (leakage, metric validity) or the methodologist lens (can the test fail, controls). Either lens counts. Module 5.

A wrong answer sends you to its module. The diagnostic does not place you in modules 3, 4, 6 and 8 to 11. For those, use the Level 4 test below.

The review blocks do not cover every module. Modules 9 to 11 have no review block. The final test has one question for each of the 11 modules, so every module can reach level 4.

Module 1. Guards that run on their own

Two hooks in .claude/hooks/ run before Claude runs a shell command. You do not start them. They do not see the commands that you type in your own terminal.

Module 1: predict

  1. Claude runs git commit -am "results". One of the changed files is results/val_scores.csv. What does the guard do?
    Answer

    The commit goes through. The split rule matches only the exact names train, val or test with .json, .csv or .tsv. A file called val.csv matches. val_scores.csv does not.

  2. A teammate pushes a branch with M3Kang data and opens a PR on the GitHub website. No Claude hook runs. Is the data safe?
    Answer

    No. The CI job m3kang-guard.yml runs the same rules and fails the check. But the commits are already on GitHub when CI runs. On 2026-11-14, main had no branch protection, so a red check did not block a merge. The history needs a rewrite.

What is wrong?

That is a work-around of a red line. The data is the problem, not the file name.

Module 2. Board and copilot

These skills come from the organizers' repository (mpous/datathon-UPC-maths-qualcomm-arduino-unoq). They know the Arduino UNO Q and the predict.py contract: one letter from A to E per problem, at most 60 s each, no network.

Module 2: predict

  1. You want the language model to write one line of reasoning before the letter. Predict the effect on time and accuracy on the board.
    Answer

    The m3kang-copilot skill has the measurement. One line of reasoning took about three times as long per problem as the baseline, and accuracy went down. The numbers are in BOARD_SETUP step 11.3. More text from the language model is not free on this board.

  2. Which file do the organizers run on the hidden test: predict.py in the root or santolina_tutor/templates/modeling/predict.py?
    Answer

    The root predict.py. It is the organizers' contract. The other file is a cookiecutter template. Do not merge them.

Module 4. Code style: ponytail

ponytail makes Claude write the smallest change that solves the task. It never cuts validation, data-loss handling, security or accessibility.

Module 4: predict

  1. In full mode, Claude skips a cache for the RAG index. How do you find that shortcut a month later?
    Answer

    Claude leaves a comment of the form shortcut: <limit>, <upgrade path>. ponytail-debt lists these comments.

  2. Does ponytail-gain tell you how many lines ponytail saved in Santolina_tutor?
    Answer

    No. It shows the authors' benchmark only. Measure your own diff with git diff --stat.

Module 5. Review and quality

Module 5: predict

  1. You want a review of your branch before the PR, not of the whole repository. Which ponytail skill?
    Answer

    ponytail-review. It reads the change and the code it connects to. ponytail-audit reads the whole repository.

  2. You give the adversarial-reviewer agent of /devils-advocate:adversarial-review your own summary of the change together with the code. What goes wrong?
    Answer

    The reviewer tends to agree with your summary. Give it the code or the document, not your conclusion. That is why adversarial-review starts fresh agents with no context.

The lenses of adversarial-review that matter most for this team:

Trap. "Round 3 still has findings, so I run round 4."

What is wrong?

When new findings come from the last fixes, the loop feeds itself. Use the adjudicator agent and stop.

Module 7. Documentation

Module 7: predict

  1. You ask the docs fixer to update the README. It finds a command that it cannot check against the code. What does it do?
    Answer

    docsjanitor does not guess. It marks the finding as a decision and asks you in a grilling round. It never invents a fact.

  2. asd-ste100 rewrites "the model may fail on long problems". Can the result say "the model fails on long problems"?
    Answer

    No. "May" is part of the claim. The skill keeps hedges, and its linter never flags them.

  3. You edit docs/BOARD_SETUP.md by hand while /docs-review is at the repair stage of that file. What happens at the next check (the subcommand of the ledger script docs_status.py that compares the ledger with the files)?
    Answer

    check fails with "changed outside the review". The skill shows you the diff and asks: start again from the audit, or accept your change.

Case: RAG examples, from idea to PR

You want to add 2 similar solved examples from the RAG index to the prompt. You must measure the effect on accuracy and time. You must show that no example is the same problem as the question. The PR needs a chart and updated documentation. Write the chain of tools in order before you open the answer.

Answer
  1. structured-planning: a plan with a check per step (optional).
  2. m3kang-copilot: build it, run eval.py, add rows to ablations.csv. Use unoq-board only if a model service fails during the experiment.
  3. adversarial-review: lens data-scientist or methodologist on the result.
  4. vis-design: a chart of accuracy and time, with and without RAG.
  5. vis-value-critique: a critique of the chart.
  6. docsjanitor: update README and BOARD_SETUP.
  7. pre-pr: simplify, docs check, draft PR.

m3kang-guard and pr-gate run on their own when Claude runs git and gh.

The case passes if your chain has these 5 parts:

  1. m3kang-copilot for the measurement.
  2. A review: adversarial-review with the data-scientist or methodologist lens, or code-review.
  3. vis-design and then vis-value-critique.
  4. A docs step: docsjanitor, doc-authoring, or the docs step of pre-pr.
  5. pre-pr.

Order counts in three places only: the measurement comes first, vis-design comes before vis-value-critique, and pre-pr comes last.
