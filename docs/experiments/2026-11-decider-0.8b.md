# Experiment: decider-0.8b vs the Qwen3.5-0.8B baseline

Laptop run, 2026-11-14, branch `exp/decider-0.8b`.

## Summary

- **Result: no improvement shown.** On 789 validation problems, decider-0.8b scores
  24.0 % and the baseline 22.4 % (+1.6 pp, exact McNemar p = 0.50).
- **Every run is at chance level**, overall and in every slice. On this split,
  always answering D gives 22.7 %.
- **The OCR limitation does not explain this.** In the slice where the model gets the
  full problem text and all five options, no model beats chance either.

## Why we tried decider-0.8b

[Mapika/decider-0.8b](https://huggingface.co/Mapika/decider-0.8b) is an open clone of
Jev, a closed one-pass decision model. It was **not** the best open Jev clone at math.
Our research found that none of them is good at hard math, because they answer in one
pass without reasoning. In the SO-Arena benchmark
([paper in the vault](../vault/papers/jev/li2026_so_arena_2611.15777.pdf)) the best
math scores come from:

- the 31B one-pass models (Sieve-31B-v3, KnowLine-31B), which are too large for the board;
- StartLux Auto 4B, which reasons when it pays off. Thinking lifts its Math score
  from 50.8 to 92.5.

We picked decider-0.8b because it is **the only Jev clone that fits the UNO Q** (see
the [board constraints guide](../GUIA_RESTRICCIONES_UNOQ.html)), and the easiest to
fine-tune and prune later:

- **Same base as the copilot.** It is fine-tuned from Qwen3.5-0.8B-Base, so it has the
  same architecture and tokenizer as the baseline. The pinned llama.cpp runs it after a
  `convert_hf_to_gguf.py` conversion.
- **Same way of answering.** It picks the option whose letter has the highest
  probability. That is what our grammar `root ::= [A-E]` does at temperature 0.
- **Open.** It is Apache-2.0, and its training scripts are public.

The other small clones fail a hard constraint:

- kev-0.8b needs its own scoring head, which llama.cpp cannot run.
- Tev1-0.8B has no licence yet.
- decider-2b is too slow for the 60 s limit.

**The expectation was modest.** Its model card says that on multiple choice it scores
close to the base model. The question was whether its decision fine-tuning improves how
the baseline picks a letter, at no cost in size or speed.

## Hypothesis and decision rule

The rule was fixed before any run. decider counts as better only if all three hold:

- it gains at least 5 pp overall;
- exact McNemar p < 0.05 against the baseline;
- it loses no more than 5 pp in any language.

Otherwise the result is "no improvement shown". Board latency is out of scope.

## Overall results

Accuracy with 95 % Wilson intervals.

| Run | All | cat | eng | esp |
|---|---|---|---|---|
| baseline | 22.4 % [19.7–25.5] | 23.1 % | 23.5 % | 20.3 % |
| decider | 24.0 % [21.1–27.1] | 22.4 % | 26.0 % | 23.3 % |
| Qwen + decider prompt | 20.7 % [18.0–23.6] | 20.6 % | 19.2 % | 22.5 % |

Reference floors: random guessing 20 %, always D 22.7 %.

The laptop baseline agrees with the board. On English text-only problems with all five
options it scores 21.8 % [14.5–31.6] (n = 87). The UNO Q gave 22.5 % on 40 problems of
the same kind ([`BOARD_SETUP.md`](../BOARD_SETUP.md), section 11.3).
Mean time per problem on the laptop is 0.42–0.46 s for all three runs.

## The OCR limitation

M3Kang gives the options A–E inside the problem image. `prepare_m3kang.py` reads them
with OCR (RapidOCR). Two facts limit what the model sees:

- **The OCR finds all five options or none.** In the validation split it found them for
  480 problems and none for 309. No problem has a partial set.
- **About half the problems need a figure** that a text-only model cannot see. The
  dataset marks the others as `text_only`.

That gives four slices:

| | 5 options found | No options | Total |
|---|---|---|---|
| Text only | **256** | 93 | 349 |
| Needs a figure | 224 | 216 | 440 |

### The clean slice: text only, 5 options (n = 256)

Here the prompt holds the full problem text and all five options. If a model can solve
these problems, it shows here.

| Run | Accuracy |
|---|---|
| baseline | 19.1 % [14.8–24.4] |
| decider | 23.0 % [18.3–28.6] |
| Qwen + decider prompt | 29.3 % [24.1–35.1] |

Floors in this slice: random 20 %, always A 26.6 %, always D 20.7 %.

**The 29.3 % is not a real result.** The letters each run answers show why:

| | A | B | C | D | E |
|---|---|---|---|---|---|
| True labels | 68 | 44 | 46 | 53 | 45 |
| baseline | 50 | 5 | 1 | 188 | 12 |
| decider | 32 | 65 | 49 | 83 | 27 |
| Qwen + decider prompt | 240 | 5 | 1 | 8 | 2 |

- **Qwen with the decider prompt answers A on 240 of 256 problems.** A is the most
  common true label in this slice, so a fixed letter scores above chance.
- **The baseline answers D on 188 of 256.** Its 19.1 % matches the always-D floor.
- **decider spreads its answers across the letters**, close to the true labels. Its
  23.0 % is just above chance, and the gap to the baseline is not significant (exact
  McNemar p = 0.25).

### The other slices

| Slice | n | baseline | decider | Qwen + decider prompt | Always D |
|---|---|---|---|---|---|
| Text only, no options | 93 | 31.2 % | 21.5 % | 15.1 % | 16.1 % |
| Figure, 5 options | 224 | 21.9 % | 22.8 % | 16.1 % | 21.0 % |
| Figure, no options | 216 | 23.1 % | 27.3 % | 17.6 % | 29.6 % |

- **Text only, no options:** the baseline's 31.2 % is the highest figure in the
  experiment. Without options the letters carry no meaning, so this is most likely its
  letter bias matching the labels of these 93 problems. We did not check this. The
  interval is wide (22.7–41.2 %), and the gap to decider is not significant (p = 0.14).
- **Figure, 5 options:** all runs sit near the always-D floor. Without the figure the
  problem cannot be solved.
- **Figure, no options:** always answering D beats all three models.

## Statistics and decision

Exact McNemar, paired by problem id and language (n = 789):

| Comparison | Only baseline right | Only other right | p |
|---|---|---|---|
| baseline vs decider | 129 | 141 | 0.50 |
| baseline vs Qwen + decider prompt | 132 | 118 | 0.41 |

Per-language change, decider minus baseline: cat −0.7 pp, eng +2.5 pp, esp +3.1 pp.

| Condition | Required | Observed | Met |
|---|---|---|---|
| Overall gain | ≥ 5 pp | +1.6 pp | no |
| McNemar | p < 0.05 | p = 0.50 | no |
| Worst language | ≥ −5 pp | −0.7 pp (cat) | yes |

**Decision: no improvement shown.** decider-0.8b is not adopted.

## What it means

- **The bottleneck is the model, not the OCR.** Even with perfect option extraction, the
  best slice stays at chance. A 0.8B model that answers with one token does not solve
  these problems, whichever weights it uses.
- **A fixed letter can look like a result.** Each run leans on one letter, and the label
  mix changes from slice to slice. Always compare a slice's accuracy with its own
  always-X floors.
- **decider changes which problems are right, not how many.** The two models disagree on
  270 problems (129 + 141), split almost evenly.

## Limitations

- **The control is not decider's starting point.** decider was fine-tuned from
  Qwen3.5-0.8B-**Base**. Our control uses the post-trained Qwen3.5-0.8B that the board
  runs. The comparison answers "is decider better than our baseline", not "what did
  Mapika's fine-tuning add". A run with Qwen3.5-0.8B-Base and the decider prompt would
  answer the second question.
- **Laptop only.** No board latency was measured. decider has the same size as the
  baseline.
- **decider is English-only** per its model card. Here it also runs on Catalan and Spanish.
- **The decider GGUF is our own conversion.** No official GGUF exists.
- **One validation split** from one shard. The slices have 93–256 problems, so their
  intervals are wide.

## Next step

Swapping one 0.8B model for another does not move accuracy. Gains have to come from the
pipeline:

- a model that reasons before it answers, within the 60 s limit;
- retrieval of solved examples (`eval.py --rag`);
- better OCR, which only pays off once the model can use the options.
